# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

WorkLedger is a cross-platform, offline-first time tracking desktop app built with **Avalonia UI** (.NET 10), backed by a local SQLite database.

All twelve build plans have merged or are in flight, and **v0.1.0 is the first real release** (the earlier `v1.0.x` tags were hand-cut packaging experiments — see "Versioning" below). `Sync/` holds a full `ISyncProvider` abstraction with two working providers (`FileSyncProvider`, `ApiSyncProvider`); `Services/SyncOrchestrator.cs` implements the last-write-wins merge; and as of plan 7 `Services/SyncCoordinator.cs` drives it at runtime from the `SyncMode` setting, wired up in `App.axaml.cs`. The Reports tab is real, computed locally by `Services/ReportsService.cs`.

**The client does no account lifecycle; the server's web portal does** (plan 12). Registration, claiming a pre-S6 server, password change and reset, device management, sign-out-everywhere, account deletion and every operator action are portal pages. This app signs an *existing* account in, syncs, and links to the portal from `AuthCapabilitiesResponse.PortalUrl`. Don't add an account operation back here — new account features are portal-only on the server side too.

The backend is a **real, separate repo**, not a placeholder: [`WorkLedger-API`](#cross-repo-workledger-api), available locally at `E:\GitHub-Repos\WorkLedger-API`. It is **C# / ASP.NET Core + EF Core + Postgres** — *not* the FastAPI service the README used to describe (corrected in plan 7).

### The shared contract, and how it's vendored

The two repos meet at exactly one place: **`WorkLedger.Contracts`**, the DTO library. Sharing *compiled types* is the entire reason the server is C# rather than Python — the compiler is supposed to catch wire drift.

The API repo publishes no package yet, so `Sync/Contracts/` in this repo is a **vendored copy** of `WorkLedger-API/src/WorkLedger.Contracts/`, pinned at a known server commit (see below). Read `Sync/Contracts/README.md` before touching anything in that folder. The rules:

- **Never edit a file under `Sync/Contracts/` to fix a client-side problem.** Those files are the server's shape. Fix it in `WorkLedger-API` and re-copy.
- Type declarations are byte-identical to upstream; the only local additions are explicit `using` directives (this project doesn't enable `ImplicitUsings`) and a provenance header.
- `Tests/WorkLedger.Tests/SyncContractGuardTests.cs` asserts the vendored constants/shapes still line up with the client's own, so a rename on either side fails the build rather than the sync. `WorkLedger-Client.csproj` grants `InternalsVisibleTo("WorkLedger.Tests")` specifically so that guard can read `LocalDbService.EntityTypes`/`SyncOperations` instead of re-stating the literals.

**Vendored state (WL-174):** re-vendored 2026-09-30 and currently verbatim against upstream **`eb743d4`** (server `main` at `414f451`), picking up S10 and S11 together. The whole difference was three trailing, defaulted parameters in `AuthDtos.cs` — `RegisterUserRequest.InviteToken`, `AuthCapabilitiesResponse.RegistrationAcceptsInvite` and `AuthCapabilitiesResponse.PortalUrl` — so nothing else needed touching; `Sync/` and `Payloads/` are byte-identical. S10's admin records and `ResetPasswordRequest` are **not** vendored: S11 moved them into the server, since the library holds only what the desktop client speaks. **Four vendored records are deliberately uncalled** — `RegisterUserRequest`, `ChangePasswordRequest`, `DeviceSummary`, `DeleteAccountRequest` — because upstream still carries them for its compatibility routes. That is not drift; they leave when upstream removes them. `SyncContractGuardTests` pins `PortalUrl` and `RegistrationAcceptsInvite` by name.

Before that, WL-133 re-vendored `3d27c86` on 2026-09-15 (server `main` at `08f02f0`). That re-vendor carried the S6–S8 auth cutover — `RegisterDeviceRequest`/`Response` removed, `LoginRequest`/`LoginResponse`/`UserSummary`/`AuthCapabilitiesResponse`/`ChangePasswordRequest`/`DeviceSummary`/`DeleteAccountRequest`/`RegisterUserRequest` added, `WhoAmIResponse` reshaped from `(AccountId, DeviceId)` to `(UserId, Email, DisplayName, DeviceId)`. **Everything under `Sync/` and `Payloads/` came through untouched** (verified file-by-file; the only diff was one XML doc word in `SyncConstants.cs`), which is what `SyncContractGuardTests` pins. Before that, WL-100 re-vendored `2065662` on 2026-08-19. The one shape change picked up was `SyncItemResult.AuthoritativeOperation` (WL-98) — an `"update"`/`"delete"` marker saying whether a server-wins payload is a tombstone. **It is consumed as of WL-101:** `ApiSyncProvider` turns a rejection carrying both a payload and an operation into a `RemoteChange` on `SyncResult.AuthoritativeChanges`, which the orchestrator merges like a pulled change; the old `RequiresFullPull` cursor rewind is now only the fallback for a winner whose operation isn't stated. Adopting the *payload* without reading the field would resurrect deleted rows, which is why the fallback still exists. `ReportDtos.cs` is deliberately not vendored (the client never calls `/reports/*`).

### The merge rule is a joint contract

Last-write-wins is implemented twice — `SyncOrchestrator.RemoteWins` here, `SyncService` there — and the two **must** stay identical. The normative statement lives in `WorkLedger-API/plans/S3-sync-endpoints.md`, restated in `plans/06-api-sync-provider.md`:

- Higher `Version` wins, strict `>`. **No timestamp tie-break** on either side (`RemoteChange` has no `CreatedAt` at all, so a server-side timestamp rule could not be mirrored). A tie leaves local untouched, which also makes replayed changes idempotent.
- A change whose `OriginDeviceId` equals this device's `DeviceId` is a self-echo and is skipped before any version comparison.
- Deletes tombstone; the server accepts them at `>=` and stores at `existing.Version + 1`.
- Push results are **positional** — one `SyncItemResult` per input change, in request order. `EntityId` is *not* a usable key: one batch legitimately carries create → update → delete for the same entity (WL-94).
- `Accepted = false` is **final** (invalid payload, or the server's row won). Those queue rows are retired, not retried. Only rows the provider said *nothing* about — a transport failure — stay pending.
- An accepted change may not have been written server-side at all (replay/self-echo is acked without a write, deliberately: an incidental write would restamp `UpdatedAt`, which is the pull cursor, and re-broadcast the row to every device).

Never "fix" a mismatch by quietly adjusting one side. Silent divergence in the merge rule is the exact bug class this arrangement exists to prevent.

## Architecture

**MVVM with CommunityToolkit.Mvvm**, single WinExe project (`WorkLedger-Client.csproj`, `net10.0`, nullable enabled, compiled bindings on by default). `Auth/` and `LocalDb/` are `<Folder Include>` placeholders in the csproj that don't exist on disk.

### Models and the versioning scheme

`Models/` holds plain `sqlite-net` POCOs. `Project`, `TaskItem`, and `TimeEntry` all implement `IVersionedEntity`:

- **`SyncId` (Guid)** — stable cross-device identity, generated once at creation, never reassigned. The `[PrimaryKey, AutoIncrement] Id` is unique only *within one device's database*; two offline devices routinely land unrelated entities on the same local `Id`. Every sync path (`SyncQueue.EntityId`, `RemoteChange.EntityId`, orchestrator merge lookups) keys off `SyncId` (WL-47).
- **`Version` (int)** — bumped on every local mutation, including deletes (WL-93). It is the sole input to conflict resolution.
- **`OriginDeviceId`** — the `AppSettings.DeviceId` of whichever install wrote the row.
- **Parent links are doubled** (WL-91): `TaskItem` carries both `ProjectId` (local int) and `ProjectSyncId` (Guid); `TimeEntry` carries `TaskItemId` and `TaskSyncId`. **The int half must never be trusted as received** — it's the authoring device's value. The orchestrator always recomputes it from the incoming `*SyncId`. Note `ProjectSyncId`/`TaskSyncId` deliberately have *no* `Guid.NewGuid()` initializer (unlike `SyncId`): `Guid.Empty` is the meaningful "parent unknown" sentinel that the backfills and the orphan re-link pass key off.

`SyncQueue` is the outbound change log: `EntityType`/`EntityId`(=SyncId)/`Operation`/`PayloadJson`/`IsSynced`. It carries no `Version` of its own — that lives on the serialized entity inside `PayloadJson`, and both providers lift it to the top level when putting a change on the wire.

### Services

- **`LocalDbService`** — thin wrapper over `sqlite-net-pcl`'s `SQLiteAsyncConnection`, constructed with a db path and the install's `DeviceId`.
  - **Conventions to preserve:** entity methods (`SaveProjectAsync`, etc.) insert when `Id == 0`, otherwise update. Every `SaveXAsync`/`DeleteXAsync` runs in **one transaction** that writes the row *and* inserts a matching `SyncQueue` entry, after stamping `Version`/`SyncId`/`OriginDeviceId` (`StampForInsert`/`StampForUpdate`/`StampForDelete`).
  - **Therefore: `SaveXAsync`/`DeleteXAsync` and the generic `Insert/Update/DeleteAsync<T>` are not interchangeable, and the split is load-bearing.** The generic helpers bypass stamping *and* the queue. Use `SaveXAsync`/`DeleteXAsync` for a **local edit** — something another device should learn about. Use the generic helpers for a write that is *not* a new local fact: `SyncOrchestrator`'s whole merge path (`WriteMergedAsync`, and the delete branches) and `RelinkOrphanedChildrenAsync`. Getting this backwards is silent in both directions: a local edit through the generic helpers never syncs, and a merge through `SaveXAsync` bumps the version, claims authorship, and queues the change straight back out — which made two devices trade ever-higher versions of an unchanged row forever, one push and pull per round (WL-99, fixed 2026-08-19; regression test `RunSyncAsync_TwoDevicesRelayingOneEdit_ConvergeInsteadOfTradingVersions`).
  - `EntityTypes`/`SyncOperations` are `internal static class` constants (`"project"`/`"task"`/`"timeentry"`, `"create"`/`"update"`/`"delete"`). Use them, never ad-hoc literals — they're the wire values, fixed by history already written into existing queue rows and sync files.
  - `InitializeAsync` creates all four tables and runs three idempotent backfills for older databases (`Version`/`OriginDeviceId`, then `SyncId`, then parent SyncIds — strictly in that order). It's fire-and-forget from the constructor, but exposed as the `Initialization` task so tests can await the schema. Note the recurring caveat documented there: `sqlite-net` leaves a mapped property at its C# initializer value when the column is SQL `NULL`, so backfill detection must go through raw SQL against the column, never through the ORM.
- **`SettingsService`** — owns `settings.json` (device-scoped, at the data directory root) and, since WL-148, a profile's `profile.json` and database path; a second constructor argument names the **profile directory** and defaults to the data directory itself, which is exactly the pre-profiles layout. `LoadSettings` overlays `profile.json` **immediately after deserializing the root file and before any backfill** — every backfill ends in a `SaveSettings`, which writes both files, so overlaying later blanked the token and the cursor on the way past. Resolves the **data directory** (`%LocalAppData%/WorkLedger`, `~/Library/Application Support/WorkLedger`, or `$XDG_CONFIG_HOME`/`~/.config/WorkLedger`). Also backup/restore (`CreateBackupAsync`, `RestoreFromDirectoryAsync`, `ValidateBackupSource`) and `ValidateSyncFolder`.
  - `AppSettings` carries the sync state: `DeviceId` (minted once at first run — there is deliberately exactly **one** of these, used as both the API device identity and the `OriginDeviceId` stamp), `SyncFolderPath`, `ApiEndpoint`, `ApiToken` + `ApiTokenExpiresAtUtc` (the server-issued JWT, not a hand-entered secret), `LastSyncedAtUtc` (the pull cursor), `SyncRetentionDays`, `SyncMode`, `SyncInterval`, `PreMergeBackupMode`.
  - **There is exactly one live `AppSettings` instance at runtime**, created in `App.axaml.cs` and shared by `MainWindowViewModel`, `SyncCoordinator` and `SettingsSyncStore`. Saving mutates that object (`MainWindowViewModel.PersistSettings`) and never builds a fresh one from the bound properties: a settings screen doesn't know about `DeviceId`, `ApiToken` or `LastSyncedAtUtc`, so a rebuilt instance writes them back empty — and a blanked `DeviceId` is re-minted on the next load, at which point the install looks like a new device to every peer and stops recognising its own rows as self-echoes. Both save paths did exactly this until plan 7.
  - Two "value == unit" conventions: `BackupInterval`'s underlying ints *are* minutes (cast straight into `Timer.Interval`), and `SyncRetentionDays` is days. `BackupInterval.OnClose = 999` is a legacy sentinel kept only so old `settings.json` files deserialize — `LoadSettings` migrates it to the standalone `BackupOnClose` bool. Keep new values consistent with this.
- **`ProfileService`** (WL-148, plan 11) — per-account profiles: one complete local database per signed-in account under `<dataDir>/profiles/<id>/`, a `profiles.json` registry at the root saying which exist and which is active, the one-time migration of a pre-profiles install into `profiles/local/`, and the **live switch** between them. Constructed in `App.axaml.cs` *before* `SettingsService`, because it is what decides which profile directory that service is pointed at.
  - **The one invariant:** the `DatabaseOwner` stamp inside `workledger.db` is **authoritative**; a registry entry is **advisory**. Backup/restore, the data-directory move and the pre-merge backups all separate a database from the files around it, so `ReconcileActiveProfileAsync` corrects the entry from the stamp — at startup and after every switch.
  - **Switching is live, and the sequence is the safety argument:** quiesce every registered `IProfileAware` in registration order (`TimerService` first — it writes to the database, so a running timer is stopped and its entry saved to the profile it was *recorded* in — then `SyncCoordinator`, then `MainWindowViewModel`), persist the outgoing profile's settings, `LocalDbService.SwitchDatabaseAsync`, `SettingsService.UseProfile`, reload the four account-scoped fields into the **one live `AppSettings` instance**, then resume. Every object keeps its identity, which is why this is a path-resolution change and not a rewiring. Never throws: a switch that cannot proceed is a failed `ProfileSwitchResult`.
  - **`DeviceId` is emphatically not per-profile.** It is the device's identity and the `OriginDeviceId` on every row this install writes; one machine that looked like several to the server would break self-echo suppression. It stays in the root `settings.json`, with the theme, the backup settings, `SyncMode` and `ApiEndpoint`. Only `ApiEmail`/`ApiToken`/`ApiTokenExpiresAtUtc`/`LastSyncedAtUtc` move into the profile's `profile.json` (they are `[JsonIgnore]`d on `AppSettings`, so each is written to exactly one file).
  - **`ReleaseActiveProfile` (WL-176, plan 12)** is the inverse of `AdoptActiveProfile`: it clears the active entry's `UserId`/`Email`/`ApiEndpoint`. It is the registry half of "Detach from account" (see `SyncCoordinator` below), and it is a named method on purpose — **don't** get the same effect by widening `ReconcileActiveProfileAsync`, whose early return on a stamp with no identity runs at startup and after every switch and decides what a restored unstamped backup does to an account's profile.
- **`SyncOrchestrator`** — drives push → pull → prune against one `ISyncProvider`, on its own `System.Timers.Timer` (`ConfigureSyncInterval`, mirroring `TimerService.ConfigureBackupInterval`'s shape); `RunSyncAsync` stays directly callable as a "sync now" entry point and returns a `SyncRunResult` (the orchestrator's own failure handling is "retry next tick", which gives a manual sync nothing to report). A `SemaphoreSlim` run lock makes a second concurrent run a no-op rather than an interleaved one. **WL-51:** an optional `preMergeBackupAsync` hook fires at most once per run, immediately before the first remote change that *overwrites or deletes* a local row (inserts don't count — nothing is at risk); the policy behind it lives in the caller's delegate, not here. Its long class comment is the authoritative statement of the merge behavior — read it before changing anything here. The non-obvious parts: remote changes are applied **parents-first** (project → task → time entry) with `RelinkOrphanedChildrenAsync` catching children that arrived ahead of their parent; a failed pull leaves the cursor alone (a failed pull is not an empty one); the cursor advances to the *provider's* reported `ServerTime`, never this device's clock (WL-92); and `PruneSyncedQueueAsync` deletes `IsSynced` rows each cycle, since nothing else bounds the queue's growth. A pull is not the only source of remote changes — `MergeRemoteChangesAsync` is the one entry point for merging, and WL-101's adopted push winners go through it too.
- **`SyncCoordinator`** — the runtime owner of sync (plan 7). Maps `AppSettings.SyncMode` to a provider (`NullSyncProvider`/`FileSyncProvider`/`ApiSyncProvider`), holds the one `HttpClient` (injectable, so the sign-in path is testable without a server), rebuilds the orchestrator only when the sync settings actually change — the key includes `ApiEmail`, so a changed identity never reuses a provider bound to the previous session — starts/stops the tick from `SyncInterval`, supplies the `PreMergeBackupMode`-gated backup delegate (snapshots into `<dataDir>/pre-merge-backups/<timestamp>`, keeping 5), and exposes `SyncNowAsync`/`SignInAsync`/`SignOut`/`ApiAuth`/`DescribeAuthState`/`SyncCompleted` — which is all `MainWindowViewModel` sees of the sync stack. **Never throws:** a misconfiguration or a dead server comes back as a failed `SyncRunResult`.
  - **`GetCapabilitiesAsync`/`WhoAmIAsync`/`ConsecutiveFailedSignIns` (WL-146).** There is exactly **one** `ApiSyncProvider` instance (`EnsureApiProvider`, keyed by endpoint), shared by the orchestrator's sync calls and everything the auth panel does — two instances would let the timer discover a revocation the UI never hears about, since the 401 verdict lives on whichever instance saw it. Plan 12 removed every account operation from this class (registration, claim, devices, password, sign-out-everywhere, deletion — they are portal pages now); what it gained instead is the two methods below, both of which exist because the client cannot see what happens in the portal.
  - **`ForgetServerVerdict` — "I've reset my password" (WL-176, plan 12 item 6). Sends nothing.** A reset redeemed in the portal clears the server's lockout counters, but the provider holds its `LockedOut` verdict until `Retry-After` lapses and is cached by endpoint, so Sign in would stay disabled for up to `Auth:LockoutMinutes` against a server that would accept the new password now. This drops the cached provider exactly as `OnProfileChangedAsync` does (and borrows nothing else from the profile machinery — the account and database are the same), resets the failure count, and discards the stored token, because a reset rotates the security stamp and a kept token would read as "signed in" until a request proved otherwise. **It refuses outside a lockout.** Invariant L is untouched: with no token the timer has nothing to run, and the next request is the user's own sign-in — a still-locked account just gets `423` again.
  - **`DetachFromAccountAsync` — "Detach from account" (WL-176, plan 12 item 7).** The user-invoked replacement for WL-143's automatic release, for an account deleted or abandoned in the portal: otherwise the `DatabaseOwner` stamp keeps naming a dead account and the next sign-in (even the same person re-registered, with a new `UserId`) strands the data in a fresh profile. **Both halves are required** — `LocalDbService.ReleaseDatabaseOwnerAsync` *and* `ProfileService.ReleaseActiveProfile` — because the adopt-in-place branch needs the stamp unclaimed *and* the profile owned by nobody. It clears the account-scoped `ApiEmail`/token/`LastSyncedAtUtc`, drops the cached provider, and is **refused while signed in** (and on data that was never attached). **Not one project, task, entry or `SyncQueue` row is touched** — the unsent queue is exactly what the next account wants pushed; `ProfileServiceTests` asserts it by count, and shows that releasing the stamp alone still strands the data.
  - **WL-138, the account-ownership guard, lives in `SignInAsync`** because that is the only moment the app learns which user it is talking to. The local database has no user column, so signing in as a different account would push one user's rows into another's and pull theirs back, irreversibly, with **every server-side check passing** — the server cannot see it and will not warn. The owner is stamped in a one-row `DatabaseOwner` table **inside `workledger.db`**, not in `AppSettings`: backup/restore and the data-directory move are supported operations that separate settings from database, and a settings-based guard is defeated by both. Same account = matching normalized email **and** `UserId`; a changed `ApiEndpoint` warns rather than blocks. An unstamped database is adopted with **no prompt whatsoever** (the offline-first path), adoption nulls `LastSyncedAtUtc` (account-scoped state in a global field), and a mismatch is **refused**, not confirmed. `SignOut` clears the token and nothing else.
  - **WL-148 turns that refusal into a four-way decision**, in this order: stamped for this account → stay; a profile already registered for this account → **switch to it** (ahead of adoption deliberately — one account must never end up with two profiles); unclaimed *and* its profile belongs to nobody → **adopt in place**, still with no prompt; otherwise → create a profile and switch. **If the switch fails, the sign-in is refused exactly as before** — a coordinator constructed without a `ProfileService` (every pre-WL-148 test) still refuses, which is why those tests are untouched. One thing needs care: `ApiSyncProvider` writes the issued token into the live `AppSettings`, which until the switch still belong to the *outgoing* profile — so `SwitchProfileForSignInAsync` restores that profile's own session before switching (the switch persists it on the way out) and writes the issued token into the new profile afterwards. Both accounts keep a working session.
- **`ReportsService`** — the local weekly rollup behind the Reports tab, plus `ToCsv`. **`StartOfIsoWeek` is the single definition of "this week" in the codebase (WL-102)** — Monday-start ISO weeks, matching the server's `ReportRange`. The Projects tab's header total and the Reports tab both call it; don't add a second week-start expression anywhere.
- **`TimerService`** — the single active timer (`System.Timers.Timer`, 1s tick) plus a separate backup timer (`BackupTick` event, `RunOnCloseBackupAsync` with a timeout). Mutates `AppStateService` (`ActiveTask`/`ActiveTimeEntry`) directly; `StartTimerAsync`/`StopTimerAsync`/`SwitchTaskAsync` are the only entry points, and only one timer runs at a time. Its writes go through `LocalDbService.SaveTimeEntryAsync` so timer-created entries are queued for sync (WL-97).
- **`AppStateService`** — tiny mutable shared-state holder passed by reference into `TimerService` and `MainWindowViewModel`. Not an event bus.
- **`ThemeService`** — swaps `Assets/themes/{Light,Dark}Theme.xaml` into `Application.Current.Resources.MergedDictionaries`. Must run on the Avalonia UI thread (dispatches via `Dispatcher.UIThread` if called off-thread).
- **`ToastService`** — spawns a transient `ToastWindow` positioned relative to `desktop.MainWindow`.

### Sync layer (`Sync/`)

- **`ISyncProvider`** — `PushAsync(IEnumerable<SyncQueue>)` / `PullAsync(DateTime since)`. Implementations are expected to be **total**: a transport failure comes back as a failure-flagged `SyncResult`/`PullResult`, not a thrown exception. `SyncProviderException` is the one type anything that does throw should use — `SyncMode = Api` pointed at a dead server must not take the app down.
- **`SyncResult`** distinguishes three outcomes deliberately: `AcceptedSyncQueueIds` (retired), `RejectedSyncQueueIds` (permanently refused — also retired, else they re-push forever), and `Failures` (may be transient, so anything only listed here is retried). When the server's own row won, `AuthoritativeChanges` carries the winners back for the orchestrator to merge (WL-101); `RequiresFullPull` asks it to rewind the cursor instead, and is now only the fallback for a winner that arrives without its operation stated.
- **`PullResult`** carries `ServerTime` (the next `since`) and `Succeeded` separately from an empty change list.
- **`ApiSyncProvider`** — HTTP against WorkLedger-API. `HttpClient` is injected, never constructed internally (one instance per provider on a sync timer is the classic socket-exhaustion bug). Authenticates with `POST /auth/login`; credentials arrive via a `Func<ApiCredentials?>` accessor rather than a stored string, so a sign-in form can hand over a closure that returns null afterwards, and **the password is never persisted anywhere** (`AppSettings.ApiEmail` records the decision and the seam an OS credential store would later implement).
  - **`TryGetCapabilitiesAsync` (WL-146)** — `GET /auth/capabilities`, sent **anonymously** (a stale token must not turn feature discovery into a 401) and cached for the life of the provider, which is per-endpoint. A `404` is cached as "sign-in only" — a server predating the user-accounts work is a supported thing to point at — but a *transport* failure is deliberately **not** cached, since an unreachable server has not answered and a five-second outage must not hide the lockout policy and the portal link until restart. Capabilities now supply exactly those two things: `MaxFailedLogins`/`LockoutMinutes` for the failure warning, and `PortalUrl`.
  - **Every authenticated call is a sync call** (push, pull, whoami), so a `401` has exactly one meaning: the session is dead. Plan 12 deleted the account-management calls, and with them `AdoptFreshToken` (the re-mint after `/auth/password` and `/auth/logout-all`) and the `credentialGuarded` split of an ambiguous `401` from a password-re-verifying handler. **Don't reintroduce either** by adding an account call here — account operations are the portal's. `SyncProviderException.ResponseBody` went with them (only registration's error text read it).
  - **`AuthState`/`AuthStatus` (WL-134)** — `SignedOut`/`SignedIn`/`SessionExpired`/`SessionRevoked`/`LockedOut`/`RateLimited`, derived in one place. `SessionExpired` is reached with **no request at all**, from a past `ApiTokenExpiresAtUtc`. `SessionRevoked` is deliberately not persisted — re-checking after a restart costs one authenticated request and zero login attempts.
  - **Invariant L, and why the 401 path looks the way it does.** Re-authenticating now needs a password the client doesn't store, and the server locks an account for 15 minutes after 5 consecutive failed logins — refusing the *correct* password for the duration. A background sync that answered every 401 with a login attempt would lock its own user out overnight, unattended. Since a 401 from `/auth/login` is **deterministic**, the correct automated retry count for a rejected credential is **zero**: the provider makes **at most one unattended failed login attempt per distinct credential**, discarding it at the point of rejection (`_rejectedCredential`), so no running time can reach the threshold. `423`/`429` are their own states, respect `Retry-After`, and never trigger a login. `SyncOrchestrator.RunTimerSyncAsync` additionally skips the whole run when the state isn't `SignedIn`. There is **no** proactive expiry-margin renewal any more — there is nothing left for it to call. Don't "improve" any of this into a retry; the regression test is `ManySyncCycles_AgainstAServerThat401sEverything_MakeAtMostOneLoginAttempt`.
- **`FileSyncProvider`** — sync via a shared folder (Dropbox/OneDrive/network share), no backend. One JSON file per push under `<syncFolder>/changes/`, named `<deviceId>-<yyyyMMddHHmmssfff>.json`; dedup is by **filename already returned**, not by the `since` cursor (peer clocks drift). Prunes files past the retention window after every pull pass.
- **`NullSyncProvider`** — the no-op provider used when `SyncMode = Off`.
- **`SyncRunResult`** — what one `RunSyncAsync` did, for a caller that has to say something about it. `Ran` and `Succeeded` are separate: a run skipped because another was in flight has not failed.
- **`SyncStores.cs`** — `IApiTokenStore` (the provider reads/writes the token) and `ISyncCursorStore` (only the orchestrator touches this) are separate interfaces with different owners, both implemented by `SettingsSyncStore` over the real `AppSettings`. Keeping them narrow is what stops every provider test from touching `settings.json`.

### ViewModels and Views

- **`AuthPanelState` (WL-146, reshaped by plan 12)** — a plain, Avalonia-free projection of `(AuthStatus, AuthCapabilitiesResponse?)` into everything the API sync panel shows: whether Sign in must be **disabled** (a lockout refuses the correct password, so an enabled button can only earn another 423 and burn the per-IP limit shared with every device on that network), the per-state copy, the repeated-failure warning, and — since WL-176 — the portal: `PortalUrl` exactly as advertised, **Open web portal** while signed out, **Manage account** while signed in or revoked, a no-account hint (an administrator's invite with a portal, the administrator without one — the portal has no open sign-up), and `ShowResetPasswordEscape` for exactly as long as a lockout is showing. **Never guess a portal URL from `ApiEndpoint`.** It exists as its own class so those rules are testable without a dispatcher, a database and a theme service — `MainWindowViewModel` only binds it. **Never hardcode 5 and 15** in the failure warning: they are `Auth:MaxFailedLogins`/`Auth:LockoutMinutes`, an operator may have changed either, and the warning fires at three because the server counts failures per *user*, so another device's attempts spend the same budget.
- **`PortalLink` (WL-176)** — `ToLaunchableUri`, the **only** gate between a server-supplied URL and the OS shell. Absolute `https://`, or `http://` to a loopback host; everything else (`file:`, `javascript:`, custom schemes, non-loopback `http://`, relative) is refused with a toast, never launched and never an exception. A pure function, tested in `PortalLinkTests` without launching anything; `OpenPortalCommand` calls it immediately before `TopLevel.Launcher.LaunchUriAsync`.
- `ViewModelBase` is just `ObservableObject`. `MainWindowViewModel` is the single large god-viewmodel holding all app state and `[RelayCommand]`s (project/task CRUD, timer control, settings, backup/restore, sync, reports), split across `MainWindowViewModel.cs`, `.Sync.cs`, `.Reports.cs` and `.Profiles.cs` via `partial class` (`.Profiles.cs` holds the Settings tab's profile list, the switch command, the Detach from account command, and the view model's `IProfileAware` reload). **It has exactly one constructor** (WL-67, plan 7) — the three-constructor mess is gone; extend that one. `TaskItemViewModel` wraps a `TaskItem` and reaches into the parent's internal `_localDbService` directly rather than through an abstraction.
- `Views/` — Avalonia XAML with minimal code-behind. Dialogs (`ProjectDialog`, `TaskDialog`, `ConfirmationDialog`) are shown via `ShowDialog<T>` on the desktop main window fetched through `Application.Current.ApplicationLifetime as IClassicDesktopStyleApplicationLifetime`. `ToastWindow` is a separate borderless window.
- `Converters/` — Avalonia `IValueConverter`s for XAML bindings (booleans → colors/visibility/chevrons/tags, seconds → duration strings, UTC → local time).

### App startup (`App.axaml.cs`)

Startup order is deliberately sequenced as commented "PHASE" blocks:
1. `DiscoverDataDirectory()` — reads only `DataDirectory` out of `settings.json` at the *default* location, without loading settings from the target location yet. It needs no second pass for profiles: `DataDirectory` is device-scoped and stays in the root file.
2. Construct `ProfileService(dataDirectory)` — migrates a pre-WL-148 layout into `profiles/local/` once, and resolves the active profile.
3. Construct `SettingsService` with that directory **and `profileService.ActiveProfileDirectory`**, then `LoadSettings()`.
4. Construct `LocalDbService(dbPath, appSettings.DeviceId)`, then `AppStateService`, `TimerService`, `ThemeService`, `ToastService`.
5. `profileService.Attach(settingsService, localDb, appSettings)` + `ReconcileActiveProfileAsync`, then `Register` each `IProfileAware` in quiesce order: `TimerService`, `SyncCoordinator`, `MainWindowViewModel`.
6. Construct `SyncCoordinator(localDb, settingsService, appSettings, httpClient: null, profiles: profileService)` and call `ApplyConfiguration()` — this is what starts sync at runtime. Then the (single) `MainWindowViewModel` constructor, passing the same `appSettings` instance.
7. Register `desktop.Exit` to dispose the coordinator and run a bounded (5s) on-close backup via `TimerService.RunOnCloseBackupAsync`. There is deliberately **no** on-close sync flush: `SyncQueue` is durable, so skipping it costs only latency, while a network round trip on exit would stall closing the app against an unreachable server.

There is deliberately **no** startup migration step any more: data-directory changes copy `settings.json` + `workledger.db` into the new directory immediately, in `MainWindowViewModel.BrowseDataDirectoryAsync`. The old "default → custom on every launch" copy silently overwrote the live database with a stale snapshot (WL-74). When changing data-directory/settings logic, `App.axaml.cs`, `SettingsService`, and the `BrowseDataDirectoryAsync`/`RestoreFromFolderAsync` commands must stay consistent — this area has had several fix commits (WL-46, WL-74).

### Tests (`Tests/WorkLedger.Tests`)

xUnit, referencing the app project directly (no mocking framework). Patterns to follow:

- Real SQLite files under `Path.GetTempPath()` with a GUID in the name, torn down via `IAsyncLifetime`/`IDisposable`; `await db.Initialization` before asserting on schema or backfills. File deletion retries on `IOException` (Windows file locks).
- Multi-device scenarios are built by constructing **two** `LocalDbService` instances with different `deviceId`s over different db files, and running real providers between them — see `SyncOrchestratorTests` and `FileSyncProviderTests`.
- `ApiSyncProviderTests` uses a hand-rolled `RecordingHandler : HttpMessageHandler` to script responses; `SyncOrchestratorTests` uses `FakeSyncProvider`/`FakeCursorStore`.
- `ProfileServiceTests` builds a whole install per test — its own data directory, registry, settings, database and coordinator, wired the way `App.axaml.cs` wires them — and covers both the mechanics and the sign-in rule — and, since plan 12, "I've reset my password" and Detach from account, which need a profile to show the active one does or doesn't move. The WL-138 refusal tests in `SyncCoordinatorTests` stay as they are and must keep passing.
- `SyncContractGuardTests` is the cross-repo drift guard — if it fails, the vendored contracts and the client have diverged; fix the client or re-vendor, don't relax the assertion.

## Known inconsistencies to be aware of

- **Doc drift is the recurring hazard here**, since the client, the server, and the plans each describe the same contract. `README.md` was corrected on 2026-08-19 (it had claimed a FastAPI backend, no test project, and placeholder `Sync/`) and again on 2026-08-20 for what plan 7 shipped; `.github/copilot-instructions.md` was deleted rather than corrected, having drifted the same way. `CONTRIBUTING.md` still lists `Auth/` and `LocalDb/` as placeholders, which they genuinely are (empty `<Folder Include>` entries in the csproj).
- **`TaskItemViewModel` still reaches into the parent's `_localDbService` directly** rather than through an abstraction (WL-68). Deliberately left alone by plan 7 — it was explicitly out of scope there.
- **Server-side WL-93 accommodation**: `SyncService`'s delete rule (accept at `>=`, store at `Version + 1`) was written when this client queued deletes *without* a version bump. The client now bumps (commit `2e3e379`), so that accommodation is belt-and-braces rather than load-bearing. Harmless, but don't be surprised by an accepted delete coming back at a *higher* `AuthoritativeVersion` than was pushed — that is not a rejection.
